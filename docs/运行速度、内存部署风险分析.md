# 微生物检测追踪系统：运行速度、内存与真实水体部署风险分析

## 1. 当前系统运行状态判断

当前代码已经具备完整原型能力：

- YOLO 检测
- detection 去重
- 亮斑过滤
- tracker 追踪
- confirmed 后实时计数
- best crop 更新
- CSV 汇总输出
- debug 视频写入

但从真实水体长时间部署角度看，目前代码更像“离线视频分析脚本”，还不是完全稳定的“长期实时系统”。

核心风险集中在：

```text
视频写入阻塞
内存长期增长
未 finalized track 的落盘时机
debug 视频与实时计数耦合过紧
长期运行监控不足
```

---

## 2. 运行速度风险

### 2.1 视频写入是当前最大瓶颈

当前主循环中，每一帧都会同步写视频：

```python
if writer is not None:
    writer.write(frame)
```

这意味着：

```text
检测一帧
→ 画框
→ 等视频编码/写盘完成
→ 才能处理下一帧
```

所以 `writer.write(frame)` 会直接拖慢整个主循环。

你实测：

```text
不写视频：约 42 FPS
写视频：约 23 FPS
```

说明 YOLO + tracker 本身是够快的，主要瓶颈在 debug 视频输出。

### 风险

真实水体部署时，如果相机输入是 30+ FPS，而系统写视频后只能跑 23 FPS，则会出现：

```text
摄像头产生帧速度 > 程序处理帧速度
```

对于实时摄像头，这会导致：

- 延迟越来越大
- 缓冲区堆积
- 最终被迫丢帧
- 实时计数滞后

### 建议

短期：

- 部署时默认 `SAVE_VIDEO = False`
- debug 阶段才打开视频保存
- 或降低 debug 视频 FPS，而不是每帧保存

中期：

- 异步视频写入
- 队列满时丢 debug 视频帧，不丢检测帧

长期：

- 原始视频由采集端单独保存
- 检测程序只负责实时计数、CSV、best crop
- 需要 debug 视频时离线重渲染

---

## 3. `resize` 并不一定加速

你测试过缩小 debug 视频分辨率，但 FPS 反而下降。

原因是：

```python
cv2.resize(...)
```

本身每帧也要消耗 CPU。

如果缩放比例只是 `0.8`，像素量减少约 36%，但新增了每帧 resize 成本，可能得不偿失。

### 结论

```text
小幅 resize 不一定加速
0.8 这种比例可能比较尴尬
```

如果要 resize，应该测试：

```text
0.5 scale
```

否则更建议先做：

```text
降低输出视频 FPS
```

例如每 2 帧写 1 帧，而不是每帧 resize。

---

## 4. FPS 先上升再轻微下降，不一定是危险信号

当前 FPS 打印方式是累计平均：

```python
fps_now = frame_count / elapsed
```

它不是最近 30 帧的瞬时 FPS。

因此出现：

```text
前期上升 → 中期稳定 → 后期小幅回落
```

是正常现象。

可能原因：

- YOLO / CUDA / OpenCV writer 前期 warmup
- 累计平均值逐渐收敛
- 后期目标数量变化
- 视频编码复杂度变化

### 判断标准

如果 FPS 是：

```text
23.5 → 23.0
```

问题不大。

如果是：

```text
23 → 19 → 15 → 10 → 5
```

才像长期性能退化或内存/IO问题。

### 建议

后续加入窗口 FPS：

```text
最近 30 帧 FPS
最近 100 帧 FPS
```

同时打印：

```text
len(detections)
len(tracks)
len(track_records)
```

这样才能判断 FPS 下降是否和目标数量、track 数量、内存增长有关。

---

## 5. 内存增长风险

当前代码中：

```python
track_records = {}
```

会持续保存历史 track 信息。

每个 record 里还可能保存：

```python
"best_crop": crop.copy()
```

这意味着每个 confirmed track 可能在内存里保留一张图片。

### 当前问题

代码会在 track missed 后 finalize：

```python
if tr.missed >= finalize_missed_thresh and rec["counted"]:
    finalize_track_record(rec, confirmed_writer, best_crop_dir)
```

但 finalize 后没有从 `track_records` 删除。

所以即使已经保存 CSV 和 best crop，record 仍然留在内存里。

视频结束时还有一次统一 finalize：

```python
for rec in track_records.values():
    if rec["counted"] and (not rec["finalized"]):
        finalize_track_record(rec, confirmed_writer, best_crop_dir)
```

这对离线视频没问题，但对无限实时摄像头不够稳。

### 长时间部署风险

如果水下机器人连续运行 2 小时：

- `track_records` 会越来越大
- 每个 best crop 可能占内存
- 内存持续上涨
- eventually 可能导致系统变慢或崩溃

### 建议

finalize 后立即释放：

```python
finalize_track_record(rec, confirmed_writer, best_crop_dir)
del track_records[tid]
```

但要小心：不能在遍历 `track_records` 本身时直接删除，需要用待删除列表。

---

## 6. 实时计数与最终保存逻辑没有完全解耦

当前实时计数发生在主循环：

```python
if (not rec["counted"]) and tr.hits >= confirm_min_hits:
    realtime_count += 1
    rec["counted"] = True
```

所以实时计数是可以工作的。

但 best crop 真正落盘保存是在 finalize：

```python
finalize_track_record(...)
```

如果系统一直运行、不停止：

- 已经 counted 的目标可以实时计数
- best crop 会先存在内存
- 只有 track missed 到阈值后才保存
- 如果某些 track 长期不断 reconnect，可能长期不 finalize
- 如果程序异常退出，内存中的 best crop 可能丢失

### 建议

增加更稳妥的保存策略：

1. counted 后先保存一个 provisional crop
2. 后续如果出现更好的 crop，再覆盖或另存
3. finalize 时写最终 CSV

这样可以降低异常退出导致图片丢失的风险。

---

## 7. debug 视频不应作为核心数据源

当前 debug 视频写入和主流程在同一线程，导致视频保存影响检测速度。

真实部署时应明确：

```text
核心数据：CSV + best crop + realtime count
辅助数据：debug video
```

debug 视频可以丢帧、降 FPS、异步写入。

但检测、计数、best crop 不应该因为 debug 视频而变慢。

### 建议架构

```text
主线程：
读帧 → YOLO → tracker → 计数 → best crop → CSV

视频线程：
接收画框后的 frame → 尝试写 debug video
```

当队列满时：

```text
丢 debug 视频帧
不丢检测帧
```

这样不会影响计数。

---

## 8. 视频和 best crop 不一定需要一一对应

如果采用异步写入并允许丢 debug 帧，则：

```text
best crop / CSV 是完整检测结果
debug video 是可视化参考
```

它们不再严格一一对应。

这不是错误，而是实时系统常见取舍。

必须保证 CSV 中有：

```text
display_id
track_id
best_frame
first_frame
last_frame
final_cls_id
```

这样即使 debug 视频缺帧，best crop 仍然可以追溯到原始帧编号。

---

## 9. 真实水体环境下的额外性能风险

真实水体可能比实验视频更复杂：

- 背景噪声更多
- 气泡更多
- 反光更多
- 悬浮颗粒更多
- 目标数量更多
- 水流导致位移更大
- 画面压缩和模糊更严重

这些会增加：

```text
YOLO detections 数量
deduplicate 成本
filter_blob_like_detections 成本
tracker 匹配成本
画框数量
视频编码压力
```

尤其是 tracker 匹配，如果 active tracks 和 detections 都很多，匹配成本会上升。

### 建议

每 30 或 100 帧打印：

```text
window_fps
len(raw_detections)
len(detections_after_filter)
len(tracker.tracks)
len(visible_tracks)
len(track_records)
```

这比单纯打印 FPS 更有诊断价值。

## 10. 当前代码的主要短板总结

| 风险点 | 严重程度 | 当前影响 | 长期部署影响 |
|---|---:|---|---|
| 同步视频写入 | 高 | FPS 从 42 降到 23 | 实时性不足 |
| `track_records` 不清理 | 高 | 短视频不明显 | 长时间内存增长 |
| `best_crop` 长期存在内存 | 中高 | 短视频可接受 | 异常退出可能丢图 |
| 只在 finalize 保存最终结果 | 中 | 离线没问题 | 实时系统不够保险 |
| debug 视频和主流程耦合 | 高 | 写视频拖慢检测 | 部署风险大 |
| FPS 只有累计平均 | 中 | 难诊断 | 无法判断局部卡顿 |
| 输出视频用 mp4v 同步编码 | 中高 | CPU 编码慢 | 长视频 IO 压力大 |

---

## 11. 建议修改优先级

### 第一优先级：实时清理 finalized track

目标：

```text
finalize 后保存 CSV + best crop，然后从 track_records 删除
```

收益：

- 降低长期内存增长
- 更适合 2 小时部署
- 不影响检测逻辑

---

### 第二优先级：增加窗口 FPS 和状态监控

新增打印：

```text
window_fps
active_tracks
track_records_size
raw_detections
kept_detections
visible_tracks
```

收益：

- 能判断是否越跑越慢
- 能定位 FPS 下降原因
- 能发现真实水体中误检暴涨问题

---

### 第三优先级：视频输出降级为 debug 功能

建议部署默认：

```python
SAVE_VIDEO = False
```

或：

```text
低 FPS debug video
异步写入 debug video
队列满丢 debug video frame
```

收益：

- 保障实时计数
- 避免 debug 功能拖垮主系统

---

### 第四优先级：best crop 先落盘，后更新

当前 best crop 长期留在内存。

可改为：

```text
每次出现更好 best crop 时，直接写入临时文件
record 里只保存路径
finalize 时确认最终文件名
```

收益：

- 内存更稳
- 异常退出损失更小

---

## 12. 总体判断

当前代码适合：

```text
离线视频分析
短时实验验证
模型效果调试
```

目前还不完全适合：

```text
水下机器人 2 小时连续实时部署
```

不是因为检测模型不行，而是因为工程结构还需要加强：

```text
视频写入异步化
record 实时清理
best crop 落盘策略
长期性能监控
```

最关键的一句话：

```text
检测和计数必须是主流程；
debug 视频只能是附属流程。
```

---

## 13. 对下一步代码修改的建议

建议下一步不要急着做所有优化，而是按下面顺序推进：

1. **先改 finalized track 清理机制**
   - finalize 后删除 `track_records[tid]`
   - 释放 `best_crop` 内存

2. **再加 window FPS 和状态监控**
   - 帮助判断是否真实越跑越慢

3. **再处理视频写入**
   - 先降低输出 FPS
   - 再考虑异步写入
   - 最后考虑队列满丢 debug 帧

4. **最后重构 best crop 保存**
   - 从“内存保存 crop”改成“磁盘保存路径”

这样可以最大程度避免一次性改太多，导致难以判断哪个改动产生了副作用。
